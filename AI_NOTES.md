# AI notes

## Tools

- **Claude Code (Claude Opus 5.5)** in the terminal, agent mode: spec analysis, code,
  migrations, tests, Docker and CI, running the tests and the compose stack.
- **A second Claude agent** for an independent read-only review of the finished code.

## Decided by me

- **Spec first, code second.** Before any code I had the AI list the spec's pitfalls and
  ambiguities, and settled each one up front. Work followed the spec's priorities, one
  commit per step.
- **Real Postgres in tests, plus concurrency tests.** Row locks and `ON CONFLICT` only
  exist in a real database; on SQLite the race tests would pass without checking
  anything. Parallel scenarios are tested: 25 simultaneous transfers, 10 identical
  webhooks at once, opposite A→B / B→A transfers.
- **Status codes where the spec is silent.** `insufficient_funds` is 409: the request is
  valid but conflicts with the balance, and 402 is not in the spec's list. A missing
  `Idempotency-Key` is 400, malformed JSON is 400.
- **Idempotency semantics.** Business errors are stored and replayed, as Stripe does.
  "Same body" means the same validated body (`"5"` equals `"5.00"`). Keys are scoped per
  account.
- **Webhook responses.** Duplicates and late events get 200 so the provider stops
  retrying. An unknown invoice gets 404 and is not recorded, so a real provider's retry
  can still succeed.
- **No external calls inside DB transactions.** The deposit is committed first, then the
  provider is called with timeouts. A retry is allowed only because the provider is
  idempotent on `external_id`. If the provider never answers, the deposit is `failed`:
  the client never got a `pay_url`, so it cannot have paid.
- **Strict rate limit without new infrastructure.** A sliding-window log in Postgres,
  not a fixed per-minute counter (which allows 2× bursts at a minute boundary), and no
  Redis.
- **Verify before trusting the AI.** An end-to-end smoke test runs against the real
  compose stack, and the code went through an independent review pass. Every finding
  got a regression test.
- **Code style.** No inline comments, docstrings of at most one sentence. The reasoning
  lives in the README.

## Where the generated code was wrong

1. **Deadlock in parallel transfers.** Accounts were locked `FOR UPDATE`, but inserting
   the idempotency key (FK to `accounts`) takes `FOR KEY SHARE` on the same row, so two
   parallel transfers waited for each other. Caught by
   `test_parallel_transfers_never_overdraw` (`deadlock detected`). Fixed with
   `FOR NO KEY UPDATE`.
2. **Idempotency schema that couldn't work.** `response_status` and `response_body` were
   `NOT NULL`, but the key row is inserted before the response exists. Noticed while
   writing the claim → execute → store flow. Made nullable; they are always filled in the
   same transaction.
3. **Autogenerated migration without server defaults.** Balances, credits and status had
   Python-side defaults only, so any insert outside the ORM would fail. Noticed by reading
   the migration instead of trusting it. Added `server_default`s and `CHECK` constraints.
4. **Rate limiter broke every POST.** The advisory-lock key bound a Python `UUID` as a
   text parameter, and asyncpg rejected it; 82 tests failed at once. Fixed by passing
   `str(account_id)`.
5. **500s found by the review.** Each of these gave a 500:
   - a signed webhook with a `NaN` or `\u0000` extra field (JSONB rejects both);
   - a 400-digit `X-Timestamp`;
   - a history cursor above BIGINT;
   - a non-ASCII bearer token in provider-mock.

   The review also found that reconciliation could get stuck on old deposits, and that
   the Postgres healthcheck passed before TCP was up. Each got a fix and a regression
   test.
